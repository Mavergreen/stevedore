# Build ingredients

Everything baked into what stevedore ships, and how a change to it reaches a release.

stevedore is **its own upstream**: it is versioned `YYYYMMDD.N` and nothing external releases it.

| Ingredient | Pinned in | Renovate | On a bump |
|---|---|---|---|
| stevedore's own source (own upstream) | `UPSTREAM_VERSION`: the date `self-upstream-version.sh` derives for own code | ❌ untrackable: nothing external releases it | bumping it on `main` is the decision to release |
| zlib, compiled into stevedore as a static library | `components/zlib/version` (the release) and `components/zlib/sha256` (its `zlib-<version>.tar.gz`) | ✅ github-releases manager tracks `madler/zlib` | the build fails at the fetch until `components/zlib/sha256` is the new tarball's: `.github/workflows/pins-bot.yml` writes it on the bump's branch with `sh build/pin-zlib.sh fill`, or `sh build/pin-zlib.sh` there does the same; the gz fixtures are then regenerated by hand if deflate's output moved |
| Sparkle 1.27.3, embedded in `stevedore-updater.app` | shipyard's `fetch_sparkle_framework.sh`, pinned by hash | ✅ moves with shipyard `@v1` | `@v1` moves without a pin changing, so nothing repackages by itself |
| MacOSX10.9 and 11.3 SDKs, CMake modules and fetch scripts | `Mavergreen/shipyard@v1` | ✅ github-actions manager tracks the tag | `@v1` moves without the pin changing, so nothing repackages by itself |
| clang22, the compiler | `components/clang22/version` (the release) and `components/clang22/sha256` (its `linux-x86_64` archive, which Linux builds with); on a Mac the installed `/usr/local/mavergreen/clang22` when it is that release, else its `clang22-cross` pkg, verified against the release's `SHA256SUMS` (`build/fetch-clang22.sh`) | ✅ github-releases manager tracks `Mavergreen/clang-22` | the Linux builds fail at the fetch until `components/clang22/sha256` is the new archive's: `.github/workflows/pins-bot.yml` writes it on the bump's branch with `sh build/pin-clang22.sh fill`; if the bot did not run, `sh build/pin-clang22.sh` on that branch does the same |
| stevedore, the packager of its own pkg | `components/stevedore/version` (the release) and `components/stevedore/sha256` (its pkg), fetched by `build/fetch-stevedore.sh` | ❌ untrackable by decision: a bot bump would release a new stevedore, which would bump the pin again (see the `self-pin:stevedore` deviation) | nothing: it is not a declared ingredient, so no bump of it repackages or releases by itself; moved by hand, then `sh build/pin-stevedore.sh` |

zlib is fetched from its GitHub release, `https://github.com/madler/zlib/releases/download/v<version>/zlib-<version>.tar.gz`,
and verified against `components/zlib/sha256` by shipyard's `shipyard_fetch_verified`. zlib publishes no checksum
file and its signatures need gpg, which 10.9 lacks, so the hash is pinned by hand from two sources that must agree.
For zlib 1.3.2, `bb329a0a2cd0274d05519d61c667c062e06990d72e125ee2dfa8de64f0119d16` is the SHA-256 of both
the GitHub release asset and `https://zlib.net/zlib-1.3.2.tar.gz`, and is the hash zlib.net's own page lists
for that tarball (checked 2026-10-25). `build/pin-zlib.sh` repeats the two-download check for a new version.

stevedore builds only zlib's deflate, inflate and checksum sources, with zlib's own `zconf.h`; the `gz*` file
functions are left out. Deflate runs at level 9, window 15, memLevel 8, the default strategy. The gzip member
is written by stevedore itself: MTIME 0, XFL 2, OS 3, no file name.

## Conformance deviations

- scheme: stevedore is its own upstream (no one else's release to repackage), so it versions itself by date as YYYYMMDD.N with no -mavericks.N axis
- macos-runner:oracle: ci.yml's oracle job runs on macos-26 because it compares stevedore's pkgs with what pkgbuild and productbuild write and install, and those exist only on macOS; the arm64 determinism run rides along on the same runner. Revisit if the comparisons move to recorded pkgbuild output, or if the 10.9 guest's pkgbuild and productbuild come to stand for current macOS's
- macos-runner:package: release.yml's package job runs on macos-26 for six reasons. (1) The arm64 slice is built there with clang22-cross, because shipyard's MavericksToolchain.cmake refuses an arm64 cross-build on a Linux host and clang22's Linux archive wires up only the 10.9 SDK; exit: arm64 builds on Linux once the toolchain file and clang22's Linux archive take the 11.3 SDK. (2) The Sparkle updater is built there, with Apple's clang as shipyard's updater recipe requires (RequireAppleClang), in both slices so Apple Silicon installs prompt for no Rosetta; exit: updaters cross-build with clang22 on Linux, as planned, or the flag day's Engine retires them. (3) shipyard's stage_product.sh reads the updater and writes the manifest with PlistBuddy; exit: shipyard stages without PlistBuddy. (4) build/fetch-stevedore.sh unpacks the pinned packager's pkg with pkgutil --expand-full, build/package-pkg.sh checks the written Distribution with pkgutil, and shipyard's sign_and_appcast.sh, artifact-facts.sh and stand-in-feeds.sh read the pkg with pkgutil and PlistBuddy; exit: the packager is fetched from its Linux archive, and shipyard's readers run without pkgutil. (5) build/oracle-pkg.sh builds the same staged roots with pkgbuild and productbuild, and the base component with shipyard's own build-base-component.sh, and compares the result with the release pkg; the release job also runs the fixture oracles (tests/component-oracle-test.sh and tests/product-oracle-test.sh) against the pinned stevedore, which need pkgbuild, productbuild and a sudo installer; those tools exist only on macOS; exit: the same as macos-runner:oracle's. (6) The job installs the pkg with Installer and runs its arm64 slice natively; exit: an Apple Silicon host that is not a paid macOS runner takes the job
- self-pin:stevedore: components/stevedore/version and components/stevedore/sha256 pin the stevedore that packages stevedore's own releases, and no bot moves them and no bump of them releases: a bot bump would release a new stevedore, which would bump the pin again, endlessly. They are bumped by hand, with sh build/pin-stevedore.sh, when the packager's output must change. Revisit if the bot learns to skip self-referencing pins
- arm64:build/package-pkg.sh: developers and CI on Apple Silicon run stevedore to package Mavericks artifacts, so the pkg carries an arm64 (11.0) slice beside the x86_64 (10.9) one
- linux: shipyard packages on Linux runners with stevedore, which serves producing Mavericks artifacts; x86_64 only, a tarball under opt/mavergreen/stevedore/ that shipyard's fetch_product_tar.sh fetches, no .deb
- on-target:updater-ui: the 10.9 job checks that the updater and its daily-check agent are installed at this version, but the headless guest drives no Sparkle dialog or install; exit: an automated GUI acceptance harness, or the flag day's Engine replacing the updater
- self-upstream-exclude:.mavericks-intree: the release workflow's in-tree allowlist; not in the product
- self-upstream-exclude:release-notes/**: release-note sources; not in the product
- self-upstream-exclude:comment-reasons: the conventions gate's comment config; not in the product
- self-upstream-exclude:.claude/**: an agent's settings for working in this repo; not in the product
